# slowrig AI Cluster — Architecture Decisions v0.1

## 1. Назначение

Этот документ фиксирует ключевые архитектурные решения по `slowrig AI Cluster`.

Формат:

* решение;
* причина;
* компромисс;
* когда можно пересмотреть.

Документ нужен, чтобы будущие изменения не ломали уже проверенную архитектуру.

---

## ADR-001 — Использовать Docker Compose как основной способ управления сервисами

Дата: 2026-06-19
Статус: принято

### Решение

Все основные сервисы кластера запускаются через Docker Compose.

### Причина

Docker Compose даёт:

* воспроизводимость;
* изоляцию сервисов;
* понятное описание инфраструктуры в YAML;
* возможность версионировать конфигурацию через git;
* простое добавление новых сервисов: gateway, memory, Telegram bot, monitoring.

### Компромисс

Docker добавляет слой абстракции. Для GPU-сервисов нужно внимательно следить за NVIDIA Container Toolkit, runtime и пробросом GPU.

### Когда пересмотреть

Если потребуется Kubernetes, Nomad или другой orchestrator. На текущем домашнем этапе это избыточно.

## ADR-002 — Использовать llama.cpp server как inference backend

Дата: 2026-06-19
Статус: принято

### Решение

Inference моделей выполняется через `ghcr.io/ggml-org/llama.cpp:server-cuda`.

### Причина

`llama.cpp` подходит для текущего стенда, потому что:

* поддерживает GGUF;
* достаточно лёгкий;
* умеет CUDA;
* даёт OpenAI-compatible API;
* позволяет явно управлять GPU offload;
* позволяет задавать multi-GPU split;
* хорошо подходит для ручного контроля на нестандартном железе.

### Компромисс

`llama.cpp` — это inference backend, а не полноценная платформа памяти, агентов, очередей и маршрутизации. Эти функции должны быть вынесены в отдельные слои.

### Когда пересмотреть

Если появится железо с большим объёмом VRAM и потребуется vLLM/SGLang/TensorRT-LLM для высокой параллельности или production-like serving.

## ADR-003 — Разделить роли моделей на `architect` и `coder`

Дата: 2026-06-19
Статус: принято

### Решение

В кластере используются две основные LLM-роли:

* `llama-architect` — тяжёлая 27B-модель;
* `llama-coder` — быстрая 9B-модель.

### Причина

У разных задач разные приоритеты:

* для простых запросов важна скорость;
* для Telegram важна отзывчивость;
* для подготовки контекста важна стабильность;
* для сложных решений важно качество reasoning;
* для аудита кода и архитектуры нужна более сильная модель.

### Компромисс

Две модели усложняют маршрутизацию. В будущем нужен gateway/router, который будет выбирать модель под задачу.

### Когда пересмотреть

Если появится одна модель, которая одновременно достаточно быстрая и достаточно качественная для всех сценариев, либо если будет добавлен более мощный GPU.

## ADR-004 — Запускать 27B на GPU 0 и GPU 2

Дата: 2026-06-19
Статус: принято

### Решение

`llama-architect` использует host GPU 0 и host GPU 2.

### Причина

27B-модель не помещается на одну P102-100 10 GB. Две карты дают около 20 GB VRAM.

GPU 0 и GPU 2 подключены через ограниченные PCIe-линии, поэтому они хуже подходят для быстрой интерактивной модели, но подходят для тяжёлой модели, где приоритет — качество, а не минимальная задержка.

### Компромисс

Медленные PCIe-линии ограничивают скорость и делают опасным интенсивный меж-GPU обмен.

Поэтому используются:

* `--split-mode layer`;
* `--tensor-split 1,1`;
* `--parallel 1`.

### Когда пересмотреть

Если:

* изменится физическое расположение GPU;
* будет добавлена карта с большим объёмом VRAM;
* появится возможность держать 27B на одной GPU;
* будут стабильные тесты другого split-режима.

## ADR-005 — Запускать 9B на GPU 1 в PCIe x16

Дата: 2026-06-19
Статус: принято

### Решение

`llama-coder` использует host GPU 1, установленную в PCIe x16.

### Причина

9B-модель должна быть самой быстрой и отзывчивой.

Она будет использоваться для:

* коротких запросов;
* Telegram;
* предварительного анализа;
* суммаризации;
* подготовки данных для 27B;
* частых worker-задач.

Для этих задач важны latency и стабильность, поэтому используется самая быстрая GPU-линия.

### Компромисс

GPU 1 остаётся занята 9B-моделью и не используется как часть 27B. Это снижает суммарную VRAM для architect-модели, но делает архитектуру более гибкой.

### Когда пересмотреть

Если:

* понадобится запускать 27B на трёх GPU;
* появится отдельная карта для fast worker;
* будет доказано, что 9B достаточно хорошо работает на x1 без потери отзывчивости.

## ADR-006 — Использовать `ctx-size 40000` для обеих моделей

Дата: 2026-06-19
Статус: принято

### Решение

Обе модели работают с `ctx-size 40000`.

### Причина

Кластер предназначен не только для короткого чата, но и для:

* длинных логов;
* нескольких файлов;
* анализа документации;
* подготовки контекста;
* работы с репозиториями;
* сложных DevOps/ML-задач.

Проверено, что обе модели стартуют и работают с таким контекстом.

### Компромисс

Большой контекст увеличивает:

* потребление VRAM;
* время prompt processing;
* риск OOM на длинных задачах;
* задержку до первого токена.

Особенно близко к пределу находится 27B на GPU 2.

### Когда пересмотреть

Если:

* появятся OOM;
* prompt processing станет слишком долгим;
* понадобится отдельный быстрый профиль для Telegram;
* будет добавлена память/RAG, уменьшающая необходимость держать большой raw-context.

## ADR-007 — Не запускать третью LLM-модель на текущем этапе

Дата: 2026-06-19
Статус: принято

### Решение

На Stage 2 не добавлять третью LLM-модель.

### Причина

Текущая пара уже покрывает основные роли:

* 9B — быстрый worker;
* 27B — тяжёлый architect.

Свободная VRAM есть в основном на GPU 1, но она нужна как запас для стабильности 9B, длинного контекста и будущих нагрузок.

### Компромисс

Не используется весь потенциальный остаток VRAM. Но кластер остаётся проще, стабильнее и легче диагностируется.

### Когда пересмотреть

Если появится конкретная роль:

* embedding model;
* reranker;
* маленькая ultra-fast Telegram-модель;
* классификатор задач;
* STT/TTS;
* vision-модель;
* отдельная summary-модель.

## ADR-008 — Оставить `parallel 1` для 27B

Дата: 2026-06-19
Статус: принято

### Решение

`llama-architect` работает с `--parallel 1`.

### Причина

27B использует две GPU через ограниченные PCIe-линии. Повышение параллельности может увеличить:

* расход VRAM;
* нагрузку на KV cache;
* меж-GPU обмен;
* задержки;
* риск CUDA allocation errors.

### Компромисс

Нельзя эффективно обслуживать несколько параллельных тяжёлых запросов к 27B.

### Когда пересмотреть

Если:

* будет доказана стабильность при `parallel 2`;
* появится gateway с очередями;
* будет больше VRAM;
* 27B переедет на более быстрые GPU.

## ADR-009 — Временно оставить Open WebUI без авторизации

Дата: 2026-06-19
Статус: временно принято

### Решение

Open WebUI работает с отключённой авторизацией.

### Причина

Стенд сейчас находится в домашней LAN и используется для быстрой настройки и тестирования.

### Компромисс

Это небезопасно для внешнего доступа. Порты `3000`, `8080`, `8081` нельзя открывать в интернет.

### Когда пересмотреть

Перед любым удалённым доступом.

Варианты:

* включить авторизацию WebUI;
* использовать VPN;
* поставить reverse proxy с auth;
* спрятать llama.cpp API за gateway;
* ограничить доступ firewall-ом.

## ADR-010 — Не хранить модели, кэш и данные в git

Дата: 2026-06-19
Статус: принято

### Решение

В git хранятся:

* compose-файлы;
* документация;
* скрипты;
* конфигурации.

В git не хранятся:

* GGUF-модели;
* cache;
* runtime data;
* логи;
* секреты;
* volume-данные.

### Причина

Модели слишком большие, кэш и данные изменчивые, секреты нельзя хранить в репозитории.

### Компромисс

Git не является полным backup всего стенда. Для моделей и данных нужен отдельный backup-план.

### Когда пересмотреть

Не пересматривать для моделей и секретов. Для некоторых статичных конфигураций будущих сервисов можно добавить отдельные safe-файлы.

## ADR-011 — Сначала документация и runbook, затем gateway/memory/agents

Дата: 2026-06-19
Статус: принято

### Решение

После Stage 1 сначала создаётся эксплуатационная база:

* `passport.md`;
* `runbook.md`;
* `README.md`;
* `architecture.md`;
* `decisions.md`;
* git baseline;
* `cluster-status.sh`.

И только потом добавляются gateway, memory, Telegram и agents.

### Причина

Без документации и baseline любое усложнение превращает стенд в набор случайных контейнеров.

### Компромисс

На старте меньше автоматизации и меньше новых функций.

### Когда пересмотреть

После завершения Stage 2 и фиксации operational baseline.

## ADR-012 — Gateway должен стать центральной точкой входа, но не добавляется сразу

Дата: 2026-06-19
Статус: предварительно принято

### Решение

В будущем нужен LLM gateway/router, но он не добавляется до завершения базовой документации и эксплуатационного слоя.

### Причина

Gateway понадобится для:

* маршрутизации 9B/27B;
* подключения Telegram;
* подключения CrewAI/OpenClaw;
* логирования;
* ключей доступа;
* будущей памяти;
* ограничения прямого доступа к backend-ам.

Но добавление gateway до стабилизации базовой схемы усложнит диагностику.

### Компромисс

Пока маршрутизация выполняется вручную через Open WebUI или прямые API.

### Когда пересмотреть

Следующий крупный этап после Stage 2.

## ADR-013 — Memory stack пока не выбран

Дата: 2026-06-19
Статус: открыто

### Решение

Пока не выбирать окончательно PostgreSQL+pgvector, Qdrant, Chroma или LanceDB.

На текущем этапе память ведётся через Markdown + git.

### Причина

Перед выбором memory stack нужно понять:

* какие данные будут храниться;
* нужен ли RAG по репозиториям;
* где будет жить история задач;
* будет ли gateway;
* какие агенты будут использовать память.

### Компромисс

Пока нет полноценной автоматической долгосрочной памяти.

### Когда пересмотреть

После выбора gateway и первых сценариев Telegram/agents.

---

## ADR-014 — Не открывать внутренние порты наружу

Дата: 2026-06-19
Статус: принято

### Решение

Порты `8080`, `8081`, `3000` не открываются напрямую в интернет.

### Причина

Сейчас Open WebUI без авторизации, а llama.cpp API не предназначены быть публичной точкой входа без защиты.

### Компромисс

Удалённый доступ пока требует нахождения в LAN или отдельного безопасного канала.

### Когда пересмотреть

Когда будет выбран вариант удалённого доступа:

* VPN;
* reverse proxy;
* gateway;
* auth;
* firewall.

## 2. Открытые вопросы

### Q1. Какой gateway выбрать?

Варианты:

* LiteLLM Proxy;
* собственный FastAPI router;
* gateway внутри OpenClaw;
* временно без gateway.

### Q2. Какую память выбрать?

Варианты:

* PostgreSQL + pgvector;
* Qdrant;
* Chroma;
* LanceDB;
* Markdown + Git на раннем этапе.

### Q3. Каким будет Telegram bot?

Варианты:

* простой chat bot;
* bot с выбором модели;
* bot с памятью;
* bot как интерфейс к агентам.

### Q4. Какие права будут у агентов?

Варианты:

* только читать;
* читать и предлагать изменения;
* выполнять команды после подтверждения;
* выполнять автономно в sandbox.

### Q5. Как делать backup?

Нужно отдельно решить backup для:

* compose/config/docs/scripts;
* моделей;
* Open WebUI data;
* будущей memory DB;
* логов;
* agent state.

## 3. Правило обновления решений

При изменении важного архитектурного решения:

1. Добавить новый ADR.
2. Не удалять старый, если он объясняет историю.
3. Указать, что старое решение superseded.
4. Сделать git commit.

Пример:

```text
ADR-015 — Replace Open WebUI direct backend config with LiteLLM Gateway
Status: accepted
Supersedes: ADR-012 partially
```
