# slowrig AI Cluster — Passport v0.1

## 1. Назначение стенда

`slowrig` — домашний локальный ИИ-кластер для разработки, анализа кода, работы с документацией, длительных аудитов, локальных ассистентов и агентских сценариев.

Кластер предназначен для:

* локального inference LLM-моделей;
* работы с кодом и логами;
* подготовки контекста для тяжёлых моделей;
* ручной работы через WebUI;
* будущего подключения Telegram-бота;
* будущего подключения CrewAI / OpenClaw / собственных агентов;
* будущей системы памяти и истории решений.

Главный принцип: серверная часть работает локально в Docker-контейнерах, модели хранятся локально, доступ осуществляется из домашней сети.

Роль: тяжёлая модель для сложных решений.

Порт на хосте:

```text

```

```text

```

Назначение:

* архитектурные решения;
* сложный DevOps/ML-анализ;
* разбор больших проблем;
* планирование задач для агентов;

## 8. Что считается проблемой

Проблемы, требующие анализа:

* контейнер перезапускается циклически;
* контейнер unhealthy;
* порт 8080 или 8081 не отвечает;
* WebUI не видит модель;
* `nvidia-smi` показывает модель не на той GPU;
* GPU 1 занята не только 9B;
* GPU 0/2 заняты не только 27B;
* VRAM растёт после каждого запроса и не освобождается;
* появляются CUDA errors;
* появляется OOM;
* 27B начинает использовать CPU layers;
* скорость резко падает;
* prompt processing становится аномально долгим;
* температура GPU уходит в опасную зону;
* Open WebUI доступен извне без защиты.

## 10. Правила изменения конфигурации

### 10.1 Не менять сразу много параметров

Любое изменение должно быть маленьким:

* один параметр;
* один сервис;
* один тест;
* затем проверка логов и VRAM.

Плохой подход:

```text
одновременно поменять ctx-size, quant, parallel, split-mode, image tag и WebUI config
```

Хороший подход:

```text
поменять только ctx-size у 9B
перезапустить только llama-coder
проверить логи
проверить VRAM
проверить короткий и длинный prompt
```

---

### 10.2 Не повышать `parallel` на x1 GPU

Для `llama-architect` правило:

```text
parallel 1
```

Причина: 27B работает на двух GPU с ограниченными PCIe-линиями. Увеличение параллельности может резко увеличить расход VRAM, нагрузку на KV cache и задержки.

---

### 10.3 Не включать CPU-offload как нормальный режим

Цель текущей архитектуры — держать слои модели на GPU.

CPU-offload может позволить “запустить” модель, но на практике это даст сильное замедление и сделает поведение нестабильным для агентских задач.

---

### 10.4 Не использовать Unified Memory как штатное решение

Unified Memory может скрыть нехватку VRAM, но при нехватке памяти начнётся уход в RAM. Для медленных PCIe-линий это приведёт к резкому падению скорости.

Использовать только как диагностический эксперимент, не как production baseline.

---

### 10.5 Не открывать WebUI и llama.cpp API наружу

Текущий режим без авторизации допустим только в LAN.

Для удалённого доступа позже нужен один из вариантов:

* VPN;
* reverse proxy с авторизацией;
* отдельный gateway;
* firewall-ограничения;
* токены доступа.

## 11. Будущая архитектура ПО

Целевая схема:

```text
Пользователь / IDE / Telegram / Agent
              |
              v
        LLM Gateway / Router
              |
      --------------------
      |                  |
      v                  v
 llama-coder        llama-architect
  9B / fast          27B / deep
```

Open WebUI на текущем этапе — ручной интерфейс. В будущем он не должен быть единственным центром архитектуры.

Gateway должен будет отвечать за:

* маршрутизацию запросов;
* выбор модели;
* логирование;
* ключи доступа;
* лимиты;
* очереди;
* хранение истории;
* интеграцию с памятью;
* единый OpenAI-compatible API для клиентов.

## 12. План памяти

Память должна быть отдельным слоем, а не просто историей Open WebUI.

Нужные типы памяти:

### 12.1 История диалогов

Хранит разговоры пользователя с моделями.

### 12.2 Память решений

Хранит важные выводы:

* какие настройки работают;
* какие ошибки были;
* какие архитектурные решения приняты;
* почему выбран тот или иной компромисс.

### 12.3 Память проектов

Хранит информацию о кодовых проектах:

* структура репозитория;
* зависимости;
* архитектура;
* важные файлы;
* последние изменения;
* известные проблемы.

### 12.4 Векторная память

Нужна для поиска по:

* документации;
* логам;
* файлам проектов;
* старым решениям;
* заметкам;
* результатам аудитов.

Возможные варианты:

* PostgreSQL + pgvector;
* Qdrant;
* Chroma;
* LanceDB.

Для долгосрочной надёжности приоритетные кандидаты:

```text
PostgreSQL + pgvector
или
Qdrant
```
